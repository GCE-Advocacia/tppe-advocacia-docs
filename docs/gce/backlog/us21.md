## História de Usuário

Como equipe de desenvolvimento, quero hospedar o sistema (frontend, API, banco de
dados e arquivos) em serviços de nuvem gratuitos para que ele fique disponível
online sem depender da máquina de um membro do grupo.

## Tarefas

- Criar o banco PostgreSQL no Neon e aplicar as migrações do Alembic pela conexão direta (sem o pooler), com `sslmode=require`;
- Migrar os dados do banco de produção atual para o Neon;
- Publicar a API no Render a partir do Dockerfile do backend, com 1 worker do gunicorn e `SCHEDULER_ENABLED=false`;
- Publicar o frontend no Netlify apontando para a URL da API no Render;
- Configurar as variáveis de ambiente (secrets) no Render, no Netlify e no GitHub Actions;
- Configurar o CORS da API para o domínio do Netlify;
- Criar na API um endpoint protegido por token que executa os envios de notificações de vencimento;
- Tornar o envio de notificações idempotente, para que o mesmo e-mail não seja enviado duas vezes no mesmo dia;
- Criar um workflow agendado do GitHub Actions que chama o endpoint de notificações diariamente;
- Calcular as datas de vencimento no fuso horário `America/Sao_Paulo`, e não no fuso do servidor (UTC);
- Criar um workflow agendado do GitHub Actions que acessa `/api/v1/health` para reduzir a hibernação da API;
- Armazenar as imagens da Landing Page, as capas dos artigos e as logos em um bucket público do Neon Object Storage, redimensionando e comprimindo as imagens no upload;
- Gravar as imagens com cabeçalho de cache (`Cache-Control`), já que cada upload gera um nome novo;
- Armazenar os documentos no Google Drive do escritório ([US09](./us09.md)) usando OAuth da conta do escritório, já que o disco do Render é temporário;
- Verificar no Resend o domínio de envio dos e-mails de notificação;
- Configurar o deploy automático do frontend e da API a partir da branch `main`;
- Atualizar a documentação de deploy.

## Critérios de Aceitação

- O frontend deve estar acessível publicamente por HTTPS no Netlify;
- A API deve estar acessível por HTTPS no Render e responder em `/api/v1/health`;
- O banco de dados no Neon deve aceitar apenas conexões autenticadas e com SSL;
- As notificações de vencimento devem ser enviadas uma única vez no dia previsto, mesmo que a API esteja hibernando;
- O endpoint de notificações deve recusar requisições sem o token correto;
- Os documentos anexados, as imagens da Landing Page e as logos não devem ser perdidos após reinício ou novo deploy da API;
- Nenhum dos serviços utilizados deve gerar custo;
- O sistema não deve depender da máquina de nenhum membro do grupo;
- As credenciais de administrador devem permitir o acesso ao painel.

## Observações

- A [US20](./us20.md) fez o deploy em uma máquina de um membro do grupo. Esta história
  move o sistema para serviços de nuvem gratuitos, por pedido do professor.
- No plano gratuito do Render, a API hiberna após cerca de 15 minutos sem acesso, e a
  primeira requisição seguinte pode levar até 1 minuto. Os agendamentos do GitHub Actions
  podem atrasar em horários de pico, por isso o workflow de health check não garante que a
  API fique sempre ativa.
- Um agendador rodando dentro da API não executa enquanto ela hiberna. Por isso as
  notificações são disparadas pelo GitHub Actions: a chamada acorda a API e executa o
  envio, e um atraso do agendamento não impede o envio no mesmo dia.
- O cron do GitHub Actions usa UTC. Como o Brasil não tem horário de verão, 11:00 UTC
  corresponde a 08:00 em `America/Sao_Paulo`.
- O GitHub desativa workflows agendados após 60 dias sem atividade no repositório. Se isso
  acontecer, o workflow deve ser reativado na aba Actions.
- O plano gratuito do Render tem 512 MB de RAM e não oferece workers em segundo plano,
  por isso a API roda com 1 worker e o serviço `scheduler` separado deixa de ser usado.
- O disco do Render é apagado a cada deploy ou reinício, por isso as imagens vão para o
  Object Storage do Neon e os documentos para o Google Drive. O navegador lê as imagens
  direto do bucket, sem passar pela API.
- O plano gratuito do Neon oferece 1 GB de banco, 5 GB de Object Storage e 5 GB de
  transferência de saída por mês por projeto. As imagens comprimidas ocupam poucos MB, e o
  cabeçalho de cache evita que sejam baixadas de novo a cada visita.
- O Object Storage do Neon estava em beta quando esta história foi implementada.
- Contas de serviço do Google não têm cota de armazenamento no Drive, por isso os
  documentos são enviados com OAuth da conta do escritório.
- Sem domínio verificado, o Resend só envia e-mails para o dono da conta.
- Os limites dos planos gratuitos devem ser conferidos na hora da configuração.
